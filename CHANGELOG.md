# Changelog

All notable changes to Studium are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). A release takes the version of `apps/studium-vscode/package.json`. The sections below 0.2.0 are development lines, grouped by month, from before the first tagged release.

## Unreleased

## 0.6.2 — 2026-11-12

This release changes no behaviour of the server, of the extension or of the lessons. It links the Studium site from the registries and the Marketplace, and brings the development tools up to date.

### Changed

- **Project site.** The README (English and French), the extension's listing page and `server.json` (`websiteUrl`) link the Studium site at https://ediam.cnrs.fr/studium/, and so do the `homepage` fields of the extension and of the `studium-mcp` package. The registries and the Marketplace show it from this release.
- **Development tools.** The test runner is vitest 5.1.0 (with vite 7 for the student runtime) and the seven GitHub Actions of the workflows are on their latest majors. Nothing of the extension, the server or the lessons changes.

## 0.6.1 — 2026-11-11

This release changes no behaviour of the server or of the extension. It gives the extension a page written for the person who installs it on the Visual Studio Marketplace and Open VSX, opens the documentation with what to do first, adds a page on choosing a model, and is the first version cut with the release tools. The repository is now public.

### Added

- **A page on choosing a model.** [Choose your model](docs/start/models.md) says where a model is used (the assistant's model, required, and the optional judge), how to work with a Copilot plan or with a model that runs on your machine, and what a judge endpoint must answer: `<address>/v1/chat/completions`, the model names `studium/audit-judge` (or `LITELLM_MODEL`) and `studium/runtime-tutor`. It states that no local model has been tried. English and French, linked from the README and the portal.
- **Tools for a release.** `tools/release/version.mjs` writes the product version in the thirteen places that carry it and opens its changelog section, or checks that they agree; `tools/release/build.sh` builds and tests the release files the same way on a laptop and in the workflow; `tools/release/registries.mjs status` says, read-only, whether a version is on npm, the MCP Registry, the Marketplace and Open VSX; `tools/release/send.sh` lets the maintainer send a built release from their machine, one question per registry, skipping a registry that already has the version.

### Changed

- **The extension's page on the Marketplace and Open VSX is written for the person who installs it.** Up to 0.6.0 the registries showed the developers' README, with build commands and links that led nowhere. From this version they show a listing page, in English then French: who does what (an assistant builds a lesson, the extension shows it), how to get a first lesson in three steps, what a lesson looks like, the commands and where your data is. A registry page cannot follow a relative link, so its links to the documentation and its screenshot use the full address of this repository's `main` branch. The pages of 0.6.0 stay as they are: a registry version cannot be replaced.
- **The release workflow no longer needs long-lived tokens for npm, the Marketplace or the MCP Registry.** It proves who it is with GitHub's OIDC token (npm trusted publishing, Marketplace trusted publishing, `mcp-publisher login github-oidc`), gains the MCP Registry step it lacked, skips a registry that already has the version so that a failed run can be started again, and is switched on per registry by a repository variable. The maintainers' release page says what to configure once on each registry. None of these routes had run when this version was prepared.
- **The README starts with what to do, for a beginner and for an assistant.** "Start here" says which part does what (an assistant builds and plays a lesson; the VS Code extension shows one and does not build any), then three steps: connect your assistant, ask for a lesson, play it in VS Code. A section addressed to an AI assistant gives the six steps to help someone install and use Studium. The VS Code page gains "Get your first lesson", and `AGENTS.md` sends an agent asked to use Studium to that section. English and French.
- **The repository is public, and named `HolobiomicsLab/Studium`.** The npm package now gives that exact address, which npm compares letter for letter before it accepts a publication from the release workflow. The installation, quickstart, Claude Code and troubleshooting pages no longer say that cloning the repository or installing the plugin needs access to it. English and French.
- **The installation pages say where the packages are.** Since 0.6.0 the server is on npm (`studium-mcp`) and in the MCP Registry (`io.github.HolobiomicsLab/studium`), and the extension on the Visual Studio Marketplace and Open VSX (`holobiomicslab.studium-vscode`). The section "If a package is not published yet" becomes "Where the packages are", in English and French; the release files remain the route for a machine that cannot reach a registry. The maintainers' release page gives the routes used for 0.6.0: the extension uploaded on the publisher's page, and the MCP Registry login with an organisation token.

## 0.6.0 — 2026-11-11

This release makes Studium installable without a checkout of the repository: the MCP server as an npm package, a Claude Code plugin, an entry for the MCP Registry, and installation pages that start with the shortest route. It also finishes the documentation site. No tool changes the inputs it takes or what it returns; the server's command gains `--version` and `--help`.

### Added

- **Install without a checkout.** The MCP server is prepared as the npm package `studium-mcp`: one file, no dependency, started by an assistant with `npx -y studium-mcp`. The package now carries a README written for its users (one line per assistant, where data lives), and the command answers `--version` and `--help` instead of waiting silently on stdin. Publication to npm needs the maintainers' token; until then the same file is attached to each release as `lesson-mcp.cjs`.
- **A Claude Code plugin.** `.claude-plugin/` declares the plugin `studium` in a marketplace hosted in this repository: one command installs the server, the twelve skills and the two lesson agents (`claude plugin install studium --marketplace HolobiomicsLab/studium`).
- **An entry for the MCP Registry.** `server.json` lists the npm package under `io.github.HolobiomicsLab/studium`; the staged npm manifest claims that name.
- **A documentation site.** `tools/docs/build-site.mjs` is no longer a prototype: search in both languages without a server (case and accents ignored, `/` to focus), a button to copy each code block, a print layout, visible focus everywhere, and the revision in the footer (`--revision`). The workflow `docs-site.yml` publishes it to GitHub Pages on each push to `main` that touches the documentation, once Pages is enabled.
- A test keeps the product version in step across the extension, the server, `server.json` and the plugin.

### Changed

- **The installation pages start with the shortest route.** Add the server with `npx`, or the Claude Code plugin, or the VS Code extension; the checkout is for teachers who prepare and approve courses and for contributors. Each assistant's page gives the `npx` form first.

## 0.5.0 — 2026-11-11

This release teaches every connected assistant to say when Studium itself is at fault and to help the person report it, corrects the skills against the code, and updates dependencies. No tool changes the inputs it takes or the shape of what it returns; `get_server_info` gains one field, `feedback`, and the server's instructions one line.

### Added

- **Assistants say when Studium itself is at fault, and help report it.** When a tool fails on a call written as documented, when Studium contradicts its documentation, or when someone asks for something it cannot do, a connected assistant is now told to say so plainly, help the person on, then offer once, at a pause and never between a question and its answer, to report it or to propose the change. It drafts the text; the person posts it. A mistake in a lesson's content goes to its teacher or author, a vulnerability to the security policy. The server's instructions carry this in one line (13 lines, was 12), and `get_server_info` returns a `feedback` block with the addresses (issues, new issue, contributing, security, guide) and what a report holds and leaves out: no learner answers, names, answer keys or secrets. The new skill `studium-contribute` holds the procedure, and the other skills hand over to it. New page [Report a problem or contribute](docs/start/report-and-contribute.md), two issue forms ("Problem or difficulty", "Feature request"), and the extension declares the issue tracker.

### Fixed

- **The skills say what the code does.** A read of the eleven skills against the code corrected: the server's proposals reach a lesson played in the conversation too, and their answer goes through `submit_response {kind: "prompt"}` (`studium-suggest` said the conversation carried none; `studium-harness` did not describe them, nor the `contest` input); `skipped_scene_ids` is on a `skip_mastered` navigation, not on the completion summary (also in the description of `submit_response`), and `skip_concept` is a navigation kind; `get_server_info` no longer "lists 34 tools"; what `forget_session` names as kept; the hint a student can ask for; the fourth key class `ungraded` and what `ready_for_approval` needs; the command-line class report can lower the floor and needs `--bundle` in the durable layout; `eval/reports/` is empty on a clean checkout; the evaluation commands that need the local corpus. `studium-teacher` now covers the dashboard's sign-in and decisions on learner contributions, sending a lesson back (`receipt`), capturing passages, and correcting a lesson after a report; `studium-student` says where a remark on a lesson's content goes.
- `SECURITY.md` no longer says "version 0.1.0".

### Changed

- **Minor and patch dependency updates.** Tailwind 4.3.5 for the student runtime; fastapi 0.162.2, pydantic 2.14.3, python-multipart 0.0.33 and pytest-asyncio 1.4.1.post1 for the Python services. `astra-tools` and `astra-spec` stay at the versions recorded as the ASTRA validator (0.2.17 and 0.0.14), and Dependabot no longer proposes them: a bump goes with a fresh validator run.
- **Two development tools move a major version.** jsdom 31 for the tests and `@vscode/vsce` 4.1 for packaging the VSIX, which has the same 103 entries as before. Running the tests now needs Node 22.22.2 or newer (or 24.15 or newer) and packaging needs Node 22 or newer; Node 20 no longer runs either. What learners install is unchanged, and `engines.node` stays `>=20`.
- **react-markdown 10 in the student runtime.** The intro and concept scenes render the same HTML as with 9.1 on every demo lesson (13 documents compared), and the runtime's code is unchanged. The update also refreshes the Markdown parsing libraries it depends on (micromark, mdast and hast utilities).

## 0.4.0 — 2026-11-10

This release makes the approval record the only source of « validated », puts the decisions on learner contributions and the teacher dashboard behind credentials, redraws the lesson panel for narrow side panels, and fixes the defects found by the 10 November audits of the learner, teacher and harness paths. While the version starts with `0.`, a minor release may change tool inputs and outputs: the entries marked **Contract change** say where.

### Added

- **The teacher dashboard has a sign-in.** Set `STUDIUM_DASHBOARD_ACCESS_CODE` (at least 16 characters) on the dashboard's server: every page and route then needs a session opened at `/login` with that code (a signed cookie, 12 hours, `HttpOnly`, `SameSite=Strict`), and « Se déconnecter » / "Sign out" ends it. Without the code the pages stay readable, for one teacher on `localhost`, and the header says the dashboard is open. **Contract change:** a decision on a learner's contribution now always needs a signed-in session; without an access code the dashboard refuses every decision (`503`), where 0.3.0 let anyone who reached the port decide. The code is shared by the teachers of one dashboard and proves no identity: the reviewer's name stays the one the teacher types. Failed sign-ins are throttled per process (10 in 5 minutes). See [SECURITY.md](SECURITY.md) and the [dashboard README](apps/teacher-dashboard/README.md).

### Changed

- **A calmer lesson panel for narrow side panels.** At 380 px the first screen of a quiz now holds the question, its choices and the button to answer: one compact session line (step, detour, time left, reviews due) replaces the two-line status and voice lines, who signs the lesson is a short chip that opens to the full sentence, and the confidence scale, « Submit » and a single « Help » button sit in a bar that stays at the bottom of the panel while the scene scrolls. « Help » opens the help ladder in place; a hint appears under the question and the question field opens in the ladder. The settings wait behind a closed section, which the « ⋯ » menu also opens. The feedback screen keeps the session line and shows the learner's answer beside the key the view carries, labelled with whose key it is; a written answer is quoted above the key points.
- **Only an approval record says a lesson is validated.** The validated status, and the name learners read in « Leçon validée par … » / "Lesson validated by …", now come from the lesson's approval record (`approval.json`, `studium-approval/1`) bound to the exact bytes of `lesson.json`, never from the free text of `validated_by`. Every surface tells three states apart: approved (the reviewer named from the record), changed since approval (the existing notice), and no record, which reads « Aucune approbation enregistrée pour cette leçon. » / "No approval is recorded for this lesson." and names nobody. This applies to the authoring block, the conversation's first screen, the panels and the Claude Code pane, `list_lessons`, `review_lesson`, review sessions (validated only when every lesson they draw from has a matching record) and the concept map page. A record that is malformed, of another schema or without a reviewer name reads as no record. Self-study lessons keep their notices and never read as validated. A learner's contribution a teacher reviews (`mode: "teacher"`, `drafted_by: "learner"`, as in `community-<id>.zip`) reads « Leçon proposée par une personne de la classe, validée par … » / "Lesson contributed by a classmate, validated by …" (or the classmate sentence then « Aucune approbation enregistrée pour cette leçon. »), in the conversation, the panels, the Claude Code pane and `list_lessons`, and its key reads « clé rédigée par une personne de la classe » / "key written by a classmate", no longer « que tu as rédigée ». The shipped fixtures carry no record and now read "No approval is recorded for this lesson." until a teacher runs `approve`. The VS Code course picker and the sidebar tree show the same three states (« validée par … », « modifiée depuis sa validation », « aucune approbation enregistrée »), read from the record, and no longer print `validated_by`.

- **The institutions are named.** The README, the documentation portal and every page of the offline site now say that Studium is developed by the HolobiomicsLab within the eDIAM team of the Institut de Chimie de Nice, Université Côte d'Azur and CNRS, and thank the EUR Spectrum; `CITATION.cff` gives the author's affiliation. Text and links only, no logo.
- **The shipped atomistique lesson carries an approval record.** `fixtures/atomistique-l1` now has `approval.json`, bound to its `lesson.json`, under the displayed name « beta-testeur » given by the owner; learners read « Leçon validée par beta-testeur ». The record says no checklist and no scene opened. `validated_by` no longer holds an e-mail address. Rerunning `build_bundle.py` rewrites the lesson and makes the record stale.
- **Dependencies brought up to date.** The minor and patch updates Dependabot proposed are in: among them esbuild 0.28, tsx 4.23, Tailwind 4.3, Playwright 1.65, Tauri 2.12, fastify 5.12.8, and for the Python services fastapi 0.162, pydantic 2.14, uvicorn 0.54 and pytest 9.2. Held back: the viewer libraries (KaTeX, Cytoscape, Vega), whose versions are tied to the vendored copies and their integrity hashes; `@types/vscode`, bounded by the extension's `engines.vscode`; and `astra-tools`, pinned by an Observatory test. Dependabot no longer proposes the hand-bumped libraries (`.github/dependabot.yml`).

### Fixed

- **The panel's settings work in MCP Apps hosts.** « Quiet », the language buttons and « Replan » now reach the server: the bridge carries every action type of a list that `@studium/lesson-panel` exports from the action schema, and an action the view does not offer is refused without asking to try again.
- **The panel's keyboard and screen-reader defects found by the 10 November audit.** The focused control keeps the focus while an action is pending; the erase confirmation is a named dialog inside the panel, with « Cancel » first and Escape to cancel; the course picker and the question form are drawn inside the panel; a formula wider than the panel can be scrolled from the keyboard; the panel is the page's main region with a first-level heading; the confidence scale says what its two ends mean.
- **Feedback that says what it holds.** An answer nobody assessed no longer says « compare it with what follows » when nothing follows; a replayed question shows the key-free feedback the server returned and counts its attempts; a contest's check is announced in a card at the top of the scene; « Choose another course » is in the menu whenever the view offers it; after a question was sent, the notice says it went to the conversation.
- **The panel reads the server's new fields.** During a detour the session line and the rail show the main-path step the view gives and where the detour returns; the explanation rung says whether it explains the last answer or the screen; every answer names the scene it answers, and an answer the server refuses because the scene changed brings back the current scene with a calm notice. A question the host did not take is said as not sent. The course picker no longer shows a language the catalogue may have wrong, and a choice reached from the keyboard is never left under the sticky bar.
- **A chat reply is read more carefully.** At a verdict deck, « aucune idée », « rien compris » or « none of them look right » no longer count as « no claim is wrong »; « none flagged » is accepted only when the whole reply says so, and a list of numbers only when it is plainly that list, so a doubt (« pas sûr »), an exception or a reason with other numbers is refused in one line instead of being graded. An empty written answer is refused instead of recording an answer, revealing the key and passing the gate. A confidence sent with `reply` is kept. « Après 3, avant 1 » is read by its labels, not the order of the digits. A quiz accepts « la b je crois », « plutôt b », « d'après moi a » or the text of one choice; « je ne sais pas » points to `request_hint` instead of asking for a letter, and a question or « attends » on a reading screen no longer counts as « continue ».
- **The Claude Code pane no longer shows a verdict twice, and says what the HTML panel says.** It draws the structured feedback and reference (labelled by `reference_kind`, so « The right answer » is no longer « Key points ») or `display_markdown`, never both; it gives the reason for a detour or a replay in one line over the scene; and it shows the reviews due, the next review date and the calibration mirror that the view carried but the pane dropped.
- **The concept-map page can be built again.** `tools/concept_map_report.py export` refused every record written by the 0.3.0 server, because the record had gained the `evidence` and `contest` fields after the reader was written. The reader now validates both, including that each evidence entry names a step of the path and each contest a concept of the map. A record written by the server is kept as a test fixture, and a server-side test fails when the record's shape drifts from it.
- **A duplicate or late answer no longer answers the next scene.** `submit_response` and the panel's `respond` action take `expected_scene_id`; when another scene is on screen the answer is refused in one line and changes nothing. A typed answer sent to a reading scene (intro, concept) is refused instead of skipping it; `ack` and the learner's words still move it on.
- **Starting a lesson the learner already has open returns that session.** A second `start_lesson_session` (or `open_lesson_panel`) for the same learner and lesson in one server returns the open session where it was, with `resume.kind: "already_open"` and a line saying so, instead of a second session that saved over the first.
- **A restart during a prerequisite detour resumes on the remediation.** The detour under way is saved with the lesson state, so a learner who failed a gate comes back to the remediation question, not past the gate. A state saved by an earlier version resumes as before.
- **The end of a contest is said in the conversation.** The answer that settles a contest opens its text with the outcome and how many check answers were right; during the check questions the status line counts the minutes left from where the lesson resumes.
- **`forget_session` answers in the learner's language.** It takes an optional `language` and otherwise uses the learner's last lesson language, then the server default, so « nothing to erase » is no longer said in English to a French-speaking learner.
- **A pane granted to a client that shows none says how to go on**, and a prompt's outcome is taken in either spelling (`accept`/`accepted`, `dismiss`/`dismissed`) by `submit_response` and `panel_action`.
- **The usage report reads the streams the server writes.** `tools/interaction_report.py` refuses a stream without a `consent_granted` event, and no server code wrote one, so the report was always suppressed. The server now opens each new consented stream with one `consent_granted` event (scope B, pedagogical telemetry for the teacher), which records that the operator declared consent through `STUDIUM_TELEMETRY_CONSENT`, not that the learner clicked anything. A resumed learner's stream does not receive a second one; a stream written before this version receives none and stays refused. Five synthetic learners' streams written by the server are kept as a test fixture, and a server-side test fails when the streams' shape drifts from it. The report's `reason` names the data folder by its name and a fingerprint, not its path.
- **Telemetry of a session that is never closed is kept.** Under consent, each telemetry event is appended to the learner's stream when it is emitted, rather than at the end of the lesson, `end_session` or forget. A learner who closes the assistant mid-lesson now leaves a stream, so completion counts them as started, and a resumed learner keeps the events of the first part. Lesson-end and `end_session` writes add no duplicate lines. Completion, in `class_report` and `tools/class_report.py` alike, now counts distinct learners who completed over distinct learners who started, so a learner who resumed (and wrote `lesson_started` twice) counts once.
- **Teacher Python tools read what the server and their siblings write.** The public-context check of `experience_templates.py`, `experience_exploration.py` and `demo-grounded-exploration.py` accepts the `notation`, `authoring` and `exploration.journal` fields `get_operator_context` returns (checked against saved server replies), so the documented activity routes run again. `concept_map_report.py` reads the JSON `class_report.py` writes as well as the MCP tool's, says on the page whether a lesson is approved for this exact version, changed since its approval, or without a record, and shows the number of graded answers beside a success rate computed over them. The analytics collector starts from a checkout in the environment `requirements.txt` builds. `class_report.py` says on stderr when its rows are named by scene id, and `media_workflow.py prepare` says the request already exists.
- **An AI critique shows what to critique.** The learner side of an `ai_critique` scene carried no text at all: the claims were removed with the answer key. The scene now publishes each claim's position ("1", "2"…) and `text` as `claims_to_critique`, never its expected flaws, and the conversation, the panel, the file channel's `task.md` and the `review_lesson` preview and plan all show it.
- **`prepare_sources` refuses an HTML page.** A source that starts with `<!DOCTYPE html` or `<html`, or in which at least five tags make up a fifth of the characters, was cut into passages of markup and JavaScript. It is now refused in one line asking for the text of the page; a text with a few inline tags or with LaTeX angle brackets is still accepted.
- **A scene that reaches no concept is warned about.** `node tools/bundle_lint.mjs` (and so `review_lesson`) reports `scene_reaches_no_concept` for each scene that takes a graded answer (quiz, spot_the_flaw, ai_critique, explain_back, comparison, summary_audit, prompt_practice, communication_sim) without `concept_refs`, in the words of `experience_packet.py check`. It stays a warning.
- **The literature tutorial's example measures something.** `examples/literature-experience/author-response.json` gave three scenes no concept and one legacy `simulation` scene. Each scene now has `concept_refs`, and the matching scene is a `comparison`.
- **A question whose answer the learner was shown is not asked again as a graded question.** The lesson state records each scene whose reference a verdict released (`reference_shown`, kept across a restart; a state without it loads empty). A prerequisite gate takes another item of the concept, or opens as `gate_unassessable` when none is left, instead of asking from memory; a contest leaves those scenes out of its check questions and, with none left, the concept cannot be contested. Reviews on a later day are not affected. `bundle_lint` warns `concept_not_recheckable` for a gate or contest target with a single key-graded scene.
- **The orientation says what the screen asks.** `waiting` is `self_rating` only on the screen that served the request (a held-back or left-behind request is no longer announced, after a restart neither, and can still be rated), so the help ladder no longer opens the explanation and the reference over a quiz not answered. During a prerequisite detour the minutes left count from the scene the lesson returns to, and the view's `progress.detour` names that main-path step. `help.explains` says whether the explanation is of the last answer or of the screen.
- **Forms name their options** (`enumNames`: a quiz choice's text, a concept's title, the claim in words; the values sent are unchanged), and the panel view carries `content_language`, the lesson's own language.
- **A lesson `.zip` carries its approval.** A lesson loaded from a `.zip` (a teacher's distribution, a community bundle) never had its approval read, so an approved lesson distributed that way would have read as unapproved. The server now reads the archive's `approval.json` member, bound to the bytes of its `lesson.json` member, with the same fail-safe reading and a 64 KiB cap; a bad member never stops the lesson from loading. The demo build scripts (`fixtures/m3`, `fixtures/m6`) add `approval.json` to the zip when it matches `lesson.json`, and leave a stale one out with a warning.
- **A learner can no longer approve their own contribution, and an approval is recorded.** `POST /learner-items/{id}/decide` on scene-synth checked nothing: a learner could call it from the learner app's origin, with no credential and any reviewer name, and publish their own item, which then read as validated and teacher-drafted. Every decision (approve, reject, request revision) now needs `Authorization: Bearer $STUDIUM_REVIEW_TOKEN` (at least 32 characters, compared in constant time); unset, every decision is refused with `503`; a browser `Origin` is refused with `403` and the route has no CORS grant (the dashboard's origin is no longer allowed on scene-synth at all). The teacher dashboard now decides through its own server route, which holds the token, sets the reviewer and the time, and refuses cross-origin and non-JSON requests; the browser never calls scene-synth. An empty reviewer, one longer than 200 characters, or the author's own handle or pseudonym is refused. An approved `community-<id>.zip` carries `approval.json` (`studium-approval/1`, bound to the sha256 of its `lesson.json` member, `decision_route: "learner-contribution"`) and says `drafted_by: "learner"`; every decision is appended to `learner_decisions.jsonl` beside the item store, with the published hashes and without the token. The reviewer learners read is a name a person typed: the submissions page has a « Your name » / « Votre nom » field (remembered in the browser's local storage), shows « Leçon proposée par une personne de la classe, validée par <name> », and keeps Approve disabled until the field is filled; the dashboard route refuses an empty name, more than 200 characters, a control character or a `urn:` identifier, and scene-synth refuses a `urn:` reviewer on approve. A rejection or revision request without a typed name still records the course IRI.
- **The dashboard reads an approval record as the lesson host does.** The library called a lesson approved only when its `approval.json` also carried `checklist`, `lint`, `tool` and a dated `reviewed_at`, so a record the host and scene-synth accept (a contribution approved from the dashboard, for example) read « checked » there and « validated » to learners. The dashboard now uses the host's rule: schema `studium-approval/1`, a digest equal to the sha256 of `lesson.json`, a non-empty reviewer. Fields a record lacks are shown as absent; an unreadable record reads as no approval.

## 0.3.0 — 2026-11-09

This release adds a two-lane lesson interface, an inspectable concept map, faster ways to play and review, and fixes found in the 5 November learner trial.

### Added

- **Two ways to play one lesson.** Three MCP tools, `open_lesson_panel`, `get_panel_view` and `panel_action`, share a public lesson view across VS Code, MCP Apps and a native Claude Code pane. The server chooses an MCP Apps panel or native pane, forms, or the conversation according to what the client can render. `packages/lesson-panel` holds the shared contract, `apps/lesson-panel-ui` the HTML renderer and bridges, and `apps/claude-code-mod` the Claude Code plugin; [Lesson panels in AI harnesses](docs/start/harness-panels.md) explains setup and limits. The two-lane interface has automated contract checks, but no learner has tried it yet: a formative trial is planned.
- **Answers without a model turn.** The prototype MCP tool `play_in_forms` uses MCP elicitation to show reading, quiz, confidence and concept-map forms, including a verdict after each answer, and hands back to the conversation when a scene needs written words or the learner wants to talk. `get_companion_brief` tells the assistant what happened on the panel, pane or forms lane since it last looked, without sending scene text, answer keys or references. `tools/latency_bench.py` times conversation, agent, forms and panel routes; only its explicitly requested `--live` mode makes paid model calls.
- **A concept map with evidence.** Lessons expose concept states, prerequisites and the path travelled. `get_workflow_graph` returns the map for the conversation, and the new MCP tool `export_concept_map` writes a local record with no learner identifier or learner words. `tools/concept_map_report.py export` turns that record into a self-contained interactive page with learner and teacher viewpoints, sources, ASTRA provenance and an ARA trace; `verify` checks it. In panels and forms, a learner can contest a concept they have reached: Studium asks check questions, and the claim alone never changes mastery or skips a scene. See [Concept map](docs/learn/concept-map.md).
- **Lessons from an existing AI conversation.** `tools/conversation_sources.py` converts a Claude Code transcript or text export into `prepare_sources` input, with credential-looking strings redacted and tool results excluded by default. The `studium-from-conversation` skill drives the authoring route, while `studium-concept-map` operates the map and `studium-suggest` notices when an existing Studium feature would help.
- **A dedicated fast lesson agent.** `.claude/agents/studium-lesson.md` plays a lesson or review as a strict relay on Claude Code's fast model, and `.claude/agents/studium-explainer.md` supplies a clearly labelled deeper explanation on request. Run `claude --agent studium-lesson`, or link the two definitions into `~/.claude/agents/`; do not place the agent between another model and every answer.
- **Orientation, voices and progressive help.** Panels, panes and conversation screens show the current step, time, due reviews and what is expected; who wrote or validated the lesson; and who assessed an answer. A help ladder lets the learner try first, then ask for a reread, hint, explanation or reference. Attention, presentation-language and available-time settings, a question hand-off, due-review and map proposals, and a resume notice work across the supported surfaces. `tools/studium_statusline.mjs` prints the current status for a Claude Code status line from the durable session's local `status.json`.
- **Teacher review receipts and interaction reports.** `tools/experience_packet.py approve` gains per-scene `--opened`, `--verdict`, `--note` and `--lang` options and writes a receipt of what was actually reviewed. The new `receipt --decision returned` records a return without approving the lesson. The teacher dashboard gains a consequence-sorted review inbox, verdict and lint details, and a preview of the voice learners will read. `tools/interaction_report.py` aggregates consented panel, forms, conversation, help, contest, resume and prompt events, behind the same minimum of five learners; `--single-stream` inspects one file without that floor.
- **Development probes for panels.** `node tools/panel-probe.mjs` exercises the panel contract, and `node tools/panel-http-dev.mjs` serves a loopback-only development adapter on `127.0.0.1:3001`. The latter is not an authenticated remote deployment. `experience_packet.py approve` and `receipt` use `STUDIUM_LANG=fr` or `en` when `--lang` is absent, then the system locale; recorded files stay identical in either language.

### Changed

- **Forty MCP tools, with explicit 0.x contract changes.** The server now registers 40 tools: the six named above (`play_in_forms`, `open_lesson_panel`, `get_panel_view`, `panel_action`, `get_companion_brief` and `export_concept_map`) in addition to the 34 in 0.2.0. `submit_response` accepts two new input kinds, `prompt {id, outcome: "accepted" | "dismissed"}` and `contest {concept_id, claim: "known" | "unsure"}`, and returns the corresponding prompt or check-question payload. Panel views use `studium/panel-view/2`, adding orientation, voices, help, prompts, attention and surface fields while retaining version-1 fields. `panel_action` accepts the new `ask`, `setAttention`, `setLanguage`, `replan`, `openMap`, `closeMap`, `contest` and `prompt` actions and optional `client_ms`; `get_companion_brief` accepts optional `peek`. `play_in_forms` now also returns the companion `brief` on hand-back, and orientation `reviews_due` counts due concepts across the learner's lessons without double-counting shared concepts. Conversation replies include orientation, voices and server proposals; form hand-backs include the companion brief.
- **The local HTTP API can record self-ratings.** It now exposes the 25 lesson operations plus `rate_recall` (26 operations), so an HTTP learner can complete the requested `again`, `hard`, `good` or `easy` rating after an ungraded production answer. Other study, authoring and teacher tools remain MCP-only.
- **Teacher commands record more of the decision.** `approve` keeps its existing bundle and reviewer inputs, adds review-receipt options and refuses a `to_fix` verdict; use `receipt --decision returned` instead. Per-item verdicts reach the receipt, a `review_receipt` event is recorded under the `reviewer` role, and viewing a verdict no longer counts as opening its grading item.
- **Lesson routing avoids repeated or skipped work.** A scene with several prerequisites evaluates each one on its own answer, an item answered correctly on a detour is not asked again when reached later, and an alternate item further down the lesson resumes after the scene just left rather than skipping intervening scenes. A due review can be proposed at the first pause even when the session opened on a question, and concepts not yet shown cannot be contested.

### Fixed

- **Retry feedback stays honest.** A same-scene retry no longer exposes the answer before the learner responds, notation reminders and recall items support prerequisite gates, and scientific-asset legends remain available on the affected viewers.
- **Panels fail safely.** A lost session offers to reopen instead of leaving stale controls; verdict chips name whose key assessed the answer; a conversation or forms surface no longer draws playable controls in the MCP Apps panel; and a concept map on an opening screen no longer reports that the lesson is finished.
